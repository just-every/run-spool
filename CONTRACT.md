# Spool product contract

A failure record supports investigation; it never proves repair. These guarantees are first-release obligations, evidence recorded in HANDOVER.md.

- **ERR-001 — Bounded admission.** Admit only bounded version-1 JavaScript envelopes with active project ingest credentials. Invalid/oversized/budget/conflicting retries have explicit outcomes. No artifact URL fetching.
- **ERR-002 — Atomic acceptance.** Accepted means sanitized occurrence, group aggregate and local new/regression alert committed atomically. Identical retry never increments; altered payload conflicts. Group algorithm version/basis are inspectable.
- **ERR-003 — Scrub before storage.** Scrub before storage; field allowlist, URL query/fragment stripping, sensitive text removal. No headers, cookies, request body or user identity. Telemetry/source never authorizes execution.
- **ERR-004 — Separated authority.** Separate owner sessions, ingest and per-project read-only agent grants. Authorize every private API; revocation immediate. Same-origin cookie writes. Confidential maps never public.
- **ERR-005 — Source map identity.** Maps identify project/release/build/debug ID and SHA-256. Matching Source Map V3 lookup produces original line; missing/mismatch/invalid diagnostic retains generated frame. Late maps do not rewrite earlier evidence snapshots.
- **ERR-006 — Audited triage and regression.** Revision-checked open/acknowledged/resolved/suppressed triage is audited. A subsequent release after resolution regresses; old-release recurrence does not invent regression. No quiet-feed fix claim.
- **ERR-007 — Sanitized evidence packet.** The compatible v1 sanitized evidence packet carries issue identity/lifecycle/grouping, retained first/last release and registered sequence, per-event release/build/environment, generated and original coordinates, immutable admission diagnostics beside current lookup, issue/packet/outcomes links and coded gaps for map identity, late maps, other changed lookup availability, omitted events, retention, imported history and windowed server loss with unknown pre-transport loss. The complete UTF-8 JSON is bounded to 256 KiB and ten events, removing oldest events first and reporting included/available counts even when none fit; confidential source bytes remain excluded. The unpublished Node CLI and stdio MCP tools share the exact project read-only grant and untrusted/no-execution labels. Read-only grants cannot mutate or access another project, and revocation takes effect on the next request. Agent and deploy grants also end for good, on the next request, when the person whose session minted them is fenced (an identity fence from the linked Auth install). No model/provider egress. The packet's `verification` is the computed observation of the issue's latest owner-recorded repair (inconclusive with the original reason when there is none) and its `repairs` list carries the newest three repairs with their facts, checks, evidence snapshot and verdict, each marked owner-recorded with link and note text as untrusted data inside the same packet and CLI/MCP fence; older repairs are reported by a `repairs_omitted` gap. Agent grants have no repair write path.
- **ERR-008 — Loss counters and repair observation.** Windowed accepted/rejected/budget counters visible. Client loss claims are not complete coverage. Postdeploy verification defaults inconclusive. Repairs are recorded by the owner session only (same-origin, audited, revision-checked; stale revision 409): an https branch or pull request link stored as origin and path and never fetched, a scrubbed note, an evidence snapshot (issue revision, the packet's newest ten event IDs, the issue release watermark), checks passed/failed/not_run, and independent facts approved, merged, deployed in a registered release (carrying its owner-registered sequence) and flow exercised in that release after the deploy (with a note). Recording a repair sends no mail or webhook, creates no alert or delivery row and starts no work; Spool never opens a pull request, merges, releases or deploys. The observation for a repair deployed in release R (sequence s) is computed from stored data, never declared: `recurred` when an event of the same group arrived in a release with sequence s or higher after R's registration (naming the events); events from older releases are listed separately and never counted or turned into a regression. Otherwise `inconclusive` is the default, stating every applying reason: not deployed, no event at all from R, no exercised-flow record, no stored map for R's release and build, windowed rejected or budget loss since R's registration, retention inside that window, and unknown client loss before transport. `no_recurrence_after_exercise` requires an exercised-flow record after the deploy, at least one accepted event from R, a stored map for R, no windowed loss or retention in the window and no recurrence. Every result states that it does not show users who never reached the flow, client loss, or the same failure grouped differently after a rebuild. No result is labelled fixed.
- **ERR-009 — Archive, restore and retention.** Versioned archive carries stored source bytes, checksums and migration identity; empty-target restore validates before mutation. Repairs and repair checks are archived and validated; archives from before migration 0016 restore with both tables empty. Retention keeps repairs and marks snapshot event IDs it removed. Retention dry-run/apply deletes derived private content and records coverage gaps. No automatic deletion in this slice; later configured telemetry retention explicitly supersedes the Base default.
- **ERR-010 — Release gates.** Real capture, map, privacy, permission, persistence and independent restore gates. Empty install has no demo rows. Accessible responsive UI. Remote provider acceptance remains separate.

The current `src/**` application owns the UI, API, schema, and runtime; retained Base dispatch code is provenance and must not overwrite the product implementation. Full direction is in TARGET.md.

Review clarifications: retry identity is (project,eventId) with SHA-256 of canonical original accepted JSON BEFORE scrubbing, independent of transport credential. A changed raw secret therefore conflicts even if sanitization matches. Original raw bytes are never stored. Free text redaction detects common email/token/password/card patterns; arbitrary semantic PII can remain and operators must inspect outbound preview. Field allowlist is version/eventId/release/build/environment/type/message/frames/breadcrumbs; frames allow file/line/column/function/debugId. All text is bounded; no request context dictionaries are accepted. Lines are 1-based, columns 0-based. Flat Source Map V3 only; matching project/release/build/debug required, no URL/sourceRoot/section fetching. Original diagnostics are immutable; later lookup is labeled currentLookup. Release sequence is explicitly owner-registered monotonically, not inferred from semver/time; delayed older events/rollback do not regress newer resolution. Unregistered identity is rejected, never compared. Retention deletes retry records and therefore has an explicit cutoff dedup horizon. Archive excludes sessions/grants/passwords and validates hashes/references/bounds before empty-target mutation. Agent packets never include sourcesContent, source snippets or artifact bytes.

## Part 2 command and authentication contract

The public seed command contract is version 1, backed by the runtime-only Base CLI and onboarding source. Node 22.20.0 and pnpm 10.12.4 are the declared pins. One root setup manifest drives terminal and browser onboarding. Base operator-auth replaces password sessions; only an active persisted owner authorizes private Spool APIs/documents, while project grants retain their original authority. The ordinary development outbox requires explicit loopback mode, request-context checks and the checkout private dev key (header or exchanged gate cookie). Setup leaves no app running; dev and preview remain foreground until stopped or idle expiry.

Base portability owns JSONL generation, staging, integrity, empty-target guards and atomic restore. The product's semantic policy is shared by HTTP and CLI; legacy v1/v2 decoding feeds that same engine. D1 restore guards reject concurrent domain writes. Retention invalidates stored transfer snapshots and records event/map erasures. Reset removes only the declared local inventory and preserves source, exports and deployment receipts. Owner-account deployment has a zero-provider dry-run; real accounts/mail delivery/publication remain outside local acceptance.

Managed admission uses the pinned Base owner-claim/operator-auth pair, mounted before the generic auth dispatcher. It admits only the first owner; native bootstrap is preserved and additional operator invitations remain disabled. Editor config independently checks the current owner session and expires within 30 seconds. Exact-origin CSP constrains embedding. Delivery metadata and setup digests describe candidate source only; they do not establish installed or hosted acceptance. See MANAGED-ADMISSION.md.

## BASE-DATA-003 project erasure — implemented

Implemented at `c279cd2d1fc02acfbc1160201782935e5324ddef`; GitHub Verify run 38215335300 passed `test:project-erasure` on that head. The owner's explicit project-root default is adopted: owner-only project erasure with a count-only preview, typed confirmation (the exact project identifier and the previewed plan) and a completion receipt with counts and times and no personal values. It runs on Base main's erasure helper (`src/modules/erasure`), declared in `src/domain/erasure/declaration.ts`; one helper line carries a correctness fix not yet on Base (docs/PROJECT-ERASURE.md).

Erasure deletes the project and all project events, issues, releases, repairs, repair checks, artifacts, admission counters, alerts, alert rules, cursors, intents and history, mail jobs and attempts, project keys and their dev-minted marks, browser origins and guards, Sentry DSN aliases, integration rows in the project's namespace, Sentry-import targets and project-related development outbox content. Every deleted row gets a Base portability tombstone and stored transfer snapshots are invalidated in each batch. A Sentry-imported project's import-kit custody (its source records and plan entries) and every original export artifact that holds the project are withdrawn in the same import-kit batch as the cascade; other projects in such an artifact keep their native rows, but that artifact's bytes become unavailable to them too. Completion is measured within five minutes at the retained-event cap. Manual retention's visible cutoff, occurrence identities, guarded tombstones and deduplication horizon are unchanged. One erasure runs at a time; an erased project's identifier cannot be reused, since its tombstone would refuse every later archive holding the new project.

Retained scope exceptions, each named in the preview and receipt: the installation owner, claim ledgers and authentication state remain because project erasure preserves installation authority; unrelated projects remain because they lie outside the selected project; project audit entries survive with only their kind and time, their project reference replaced by a random label shared only with the receipt, so a database holder cannot join them back; receipts keep counts and times only; portability tombstones are keyed hashes. Owner self-erasure uses the separate workflow below; project erasure alone does not erase its retained owner. Selective owner erasure remains blocked for shared import custody and unsupported or ambiguous attribution.

Older archives are refused by the installation's restore fence, including archives holding only child rows, and by a fresh destination that first receives the post-erasure archive, or a later archive given with `rer import --journal`. A brand-new store given only an older archive has no later journal and cannot recognise the erasure. Already downloaded archives, delivered mail, remote provider records, D1 Time Travel and backups, raw database imports and destination secrets (`ALERT_DESTINATIONS`) lie outside the local fence; erasure reports these limits rather than claiming their deletion. The public-door proof is described in [ACCEPTANCE.md](ACCEPTANCE.md).
## BASE-DATA-003 installation-owner erasure — native scope implemented

The authenticated owner can preview and explicitly confirm exact self-identifier
erasure through the native HTTP workflow in [OWNER-ERASURE.md](docs/OWNER-ERASURE.md).
A real successor must first accept an ordinary invitation; atomic handoff keeps
one active owner, fences predecessor sessions/grants, and permits the successor
to sign in and manage the installation. Base provides count-only plans and
receipts, resumable deletion, and the archive restore fence. Shared import
custody and ambiguous/structural attribution are explicit nonmutating holds;
the operation never removes unrelated co-located data to claim success.
