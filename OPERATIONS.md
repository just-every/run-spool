# Operating Spool

Use Node 22.20.0 and pnpm 10.12.4. The exact public commands and flags are in [SEED-COMMAND-CONTRACT.md](SEED-COMMAND-CONTRACT.md); [README.md](README.md) gives the complete local journey. `pnpm run check -- --profile first-party` validates the portable contract before dependency installation or configuration. `pnpm run doctor` separately checks tools and configured inputs. Neither proves live provider access.

Local setup uses one `rer-setup.json` manifest and the copied Base lifecycle. Provide the real owner email through the setup prompt or declared answers, keeping it and secrets out of shell arguments; generated SESSION_SECRET and SETUP_TOKEN are managed secrets. AUTH_ORIGIN, AUTH_LOCAL, MAIL_PROVIDER and MAIL_FROM select the exact loopback development runtime and outbox. Settings belong in the ignored 0600 `.dev.vars`; private state directories are 0700. Setup refuses a conflicting email and never changes an existing operator identity. It requests ordinary sign-in and stops its temporary app. The development outbox sends no email. `/sign-in` uses a native POST form; the confirmation GET does not consume the token, and its POST works once. The product form and installer request `/setup`; explicit valid destinations are preserved. Native auth alone parses submitted input: manually missing or unsafe body destinations use its `/app` fallback, where an unfinished owner is redirected to `/setup`. Browser forms requesting HTML receive usable success or failure feedback with the native status; JSON clients retain the native JSON response.

The native dependency build allowlist contains only esbuild and workerd. CI installs Playwright's bundled Chromium with system dependencies before running the complete `pnpm verify`; browser installation diagnostics are enabled and the job has a 90-minute limit.

`pnpm run dev` and `pnpm run preview` remain foreground processes with health and outbox checks. The latter serves fixed production output. Both use `.wrangler/state`; alternate requested ports override runtime origin only. Stop them with their matching `--stop` command before changing mode, reset or transfer. Private APIs and documents recheck the active persisted owner. The exceptions are public pages without an owner session: `/` serves the static landing page (no script, its own CSP) with a Sign in link, and `/docs` serves the docs built from the repository Markdown that `docs/site.json` lists; owners keep the workbench at `/`, and every other document still redirects to `/sign-in`. A project ingest or agent key cannot authorize installation operations. Origin/CSRF checks use configured AUTH_ORIGIN, never a forwarded host. The outbox requires explicit local mode, literal loopback origin, matching request host, safe fetch metadata and this checkout's private dev-key header or exchanged gate cookie. Open the private `RER_OPEN` link printed by dev/outbox; do not share it. Dev signs in as the owner by default; `--login` requests ordinary sign-in instead.

## Existing installation recovery

Existing SQL filenames and bytes in `migrations/core` are unchanged; migrations 0004 onward are additive. Preserve the `d1_migrations` ledger. Old password sessions are inert; existing project grants, projects, maps, events, origins and audit rows remain domain data. Do not use a domain archive as an in-place migration backup: archives deliberately exclude credentials.

The former placeholder D1 identity maps to a different local SQLite resource than the current explicitly local `errors-local` identity. Setup refuses a legacy domain store without operator-auth, multiple candidate databases, linked storage, or generated-output state directories before building, rewriting secrets or migrating. It does not pick the newest store or merge databases. An interrupted partial SQL transition also requires inspecting its ledger before resuming.

Setup and archive preflight inspect a private database/WAL copy. Ordinary checkpoint/reuse tails are accepted after validating the current committed WAL generation and recognizing older reset generations; current checksum damage, incomplete frames and ambiguous generation boundaries still require explicit recovery. Inspection never checkpoints or truncates the original state. Keep the database and its WAL together when preserving an offline copy: committed owner and project changes may exist only in the WAL.

To recover deliberately, first stop every runtime and retain a complete private copy of each candidate state directory, its original Wrangler configuration and private settings. Work on a separate destination, leaving originals intact. With the original configuration and its explicitly selected `--persist-to` directory, use Wrangler's local D1 export to make a full SQL backup including credentials and migration ledger. Create a fresh canonical destination using the current local binding; import the full SQL backup with local D1 execute, preserving the original filenames/ledger, then apply only unapplied migrations from `migrations/core`. Confirm project, credential, event, map and origin counts and grant behavior in that destination before selecting it as the active checkout. Resolve or relocate every obsolete state path only after this explicit comparison. Never delete a candidate to make preflight pass.

After the recovered destination has the additive auth tables, run setup with the intended first owner email. It creates the first real owner; subsequent setup preserves it. The managed-secret helper adds missing auth settings while preserving existing secret values. Only after successful bootstrap/preservation and ordinary outbox sign-in does Spool retire the old OWNER_PASSWORD setting and `.local/owner-password.txt`. An interrupted attempt retains recoverable private state. Never copy a password session into operator-auth.

## Data movement and retention

Use `pnpm run export -- --output exports/spool.jsonl` with the app stopped. Base portability inventories all owned D1 tables, snapshots them consistently, and writes a new private archive. Authentication/owner tables, credential grants, legacy password sessions, development outbox, admission guards, portability bookkeeping and migration metadata are excluded. Private maps and browser-origin configuration are included. Configuration names, never values, are listed for recovery.

Use `pnpm run import -- --input exports/spool.jsonl --yes` into an empty domain database. Both CLI and owner HTTP restore import the same semantic policy: normalized scrubbed events, map integrity, grouping, references, audit shapes and capacities. New JSONL content, part integrity and empty-target/atomic commit are owned by Base. Strict native v1/v2 decoding translates into the same Base staging and commit; there is no legacy SQL restore loop. Restore creates neither grants nor an owner. Run setup and create new project grants afterward. Unsupported remote transfer fails explicitly. Native v1/v2 archives have a 16 MiB total input limit and a 10,000-row limit per table. Base portability JSONL instead limits each line to 24 MiB, each part to 16 MiB and each part to 1,000 rows; it has no equivalent total archive or per-table row limit. Both formats enforce the domain capacities, including 10,000 retained events, 20 maps and 20 explicit browser origins per project.

Owner HTTP transfer uses `/api/archive` and `/api/restore`; restore additionally requires `X-Confirm-Restore: yes` and same-origin owner authority. D1 triggers block domain writers while a restore is staged; Base removes and restores those triggers inside the atomic commit. Failed imports abort their staging. A process crash can leave a staged import reserved; preserve its state and inspect Base's import status/abort API before retrying. There is no silent takeover of an incomplete destructive operation.

Retention remains manual preview/apply. Its transaction removes selected event occurrences and retry identities, updates derived headlines, removes unused old map occurrences, records erasure tombstones and invalidates stored snapshots/staging. Journal writes and deletion recheck the same occurrence and current map references in that transaction. Event IDs and map keys can be accepted again with new occurrence identities; their new archives retain every older tombstone without fencing the new evidence. The apply result and audit report the number actually deleted, which can differ from an earlier preview under concurrent writes.

The additive occurrence migration preserves existing event/map bytes, grants and the migration ledger. Pre-transition rows and native v1/v2 imports carry a legacy occurrence marker; pre-transition Base JSONL archives upgrade through Base staging. Legacy occurrences remain subject to both the original natural-key tombstones and the new occurrence-key tombstones. An already ambiguous legacy row whose natural key was tombstoned remains fenced; migration does not infer whether it was reaccepted or erase journal history. Historical comparisons across the cutoff are incomplete. An owner-held exported file remains outside live retention; old legacy files cannot invent later erasure history.

Reset requires `--yes`, refuses active or unsafe state, and displays its exact inventory: `.wrangler/state`, `.rer/local`, `.seed/installer`, `.dev.vars` and `.dev.vars.previous` when present. It preserves source, dependencies, exports and `.rer/deploy` receipts. The next setup creates a fresh empty installation and owner.

Project erasure under BASE-DATA-003 is implemented: Settings → Erase this project (or `GET`/`POST /api/projects/:project/erasure`, owner session, same origin) shows a count-only preview, requires the typed project identifier and returns a receipt with counts and times. It deletes the project and everything recorded for it in one fenced cascade (see docs/PROJECT-ERASURE.md), and a Sentry-imported project's import custody and original export bytes in the same import-kit batch. Do not treat retention as project erasure. Take a private archive first if you may need the data: an archive made before the erasure is refused by this installation afterwards. Scope exceptions and external-copy limits are in [CONTRACT.md](CONTRACT.md).

## Owner-account deployment

### Sentry intake, artifacts and historical import

The implemented [switching guide](docs/SENTRY-SWITCHING.md) covers project-scoped ingest DSNs for supported JavaScript exception envelope/store intake, required release/build registration and exact browser origins. Selected exception fields and breadcrumb labels use the native scrubber; unsupported items are counted and discarded. Unmodified `@sentry/browser` and `@sentry/node` 11.6.0 verification programs exist; their actual results are recorded separately, and dependency pins alone prove no runtime behavior. The source-map CLI/Rollup/Vite plugin uses a server-side project deploy key for release registration and bounded flat map upload only. It does not upload Sentry artifact bundles or authorize ingest, evidence reads or administration. Explicit labels can also use the unpublished [workspace breadcrumbs package](packages/breadcrumbs/README.md).

Organization import is a separate owner-session operation through Base import-kit: inspect the scrubbed dry-run plan and omissions, apply the reviewed fingerprint, inspect/resume the journal and use guarded undo if needed. Only synthetic fixtures qualify the importer so far; no real export migration or feature-parity claim is accepted. Private source originals remain in the import journal, outside event retention and native archives; follow the guide's originals custody instructions before moving installations. The full verify includes these native intake, SDK, tooling and import programs; their exact-head results belong in the completion evidence, independently of hosted/provider acceptance.

### Deployment inputs

`pnpm run deploy -- --dry-run` performs the real local build, packages emitted Worker/assets plus every `migrations/core` SQL file and validates `deploy.json`. It does not contact a provider. Actual deployment requires explicit authorization, CLOUDFLARE_ACCOUNT_ID and CLOUDFLARE_API_TOKEN for an account with a workers.dev subdomain. Deploy-kit finds or creates its own declared D1 resources and generates real cloud IDs. `.rer/deploy` records resource ownership; unrelated existing resources are not adopted.

Provide OWNER_EMAIL, SESSION_SECRET, SETUP_TOKEN, MAIL_FROM, MAIL_API_KEY, ALERT_DESTINATIONS and ALERT_DESTINATION_HASH_KEY through the owner's approved secret source; [docs/HOSTED.md](docs/HOSTED.md) generates a complete private settings file (empty alert destinations, generated secrets and hash key), claims the hosted owner after the first deploy with `pnpm run hosted claim`, and gives the update recipe. The declaration selects SendGrid (`MAIL_PROVIDER=sendgrid`) and production AUTH_LOCAL=false; sender verification and mailbox delivery are owner-run acceptance work. AUTH_ORIGIN is derived by deploy-kit from the selected owner target. Health queries D1 and reports deploy-kit source/fingerprint/version metadata when configured. Hosted rollout, provider account actions, sender setup, receipts, public release and tags require separate owner authorization and evidence.

The descriptor's development-mail-outbox loop is a local Worker/D1 loop. Its hosted mail loop is disabled and optional until the owner configures delivery. Local completion must not be described as hosted mail acceptance.

## Per-project alerts

New-issue and later-release regression alerts are sent right after ingest: the admitting request expands that event's routed new-issue or regression intents and dispatches their mail and webhook deliveries through `waitUntil`, so they do not wait for the cron. The Worker cron runs every minute and evaluates complete server-received volume-window spikes, then recovers and dispatches persisted delivery jobs. Alerts that still depend on the cron: **spike** alerts (evaluated only there), **retries** of a rate-limited or failed delivery, deliveries left **queued** when the dispatch after ingest did not finish (an expired claim, a request that ended early, missing configuration fixed later), and expired-claim recovery. Every send takes a durable claim first, so the dispatch after ingest and a cron run that reach the same delivery send it once. Each scheduled run writes its time to `alert_scheduler.last_run`, idle or not; `/health` shows it as `alerts.lastScheduledRun` (null until the first run) and Settings shows it under **Scheduled alert run**, so a cron that ticks on an idle installation is told apart from one that never runs. Owners manage per-project rules for new issues, later-release regressions and spikes and inspect feed/delivery logs in Alerts. Feed transition payloads preserve the accepted release identity for later triage; retention cannot manufacture a new issue from a zero retained count. This is bounded source behavior; provider delivery and trusted egress remain separately qualified, with no Oncall dependency or Slack integration.

Configure server-only `ALERT_DESTINATIONS`, `ALERT_DESTINATION_HASH_KEY`, and optionally trusted HTTPS `ALERT_PUBLIC_ORIGIN`. Mail uses the existing explicit Base mail provider and sender. Webhooks require a separately installed, qualified `INTEGRATION_EGRESS.send(WireRequest)` RPC service, Base's egress service (`src/modules/egress-service`): no ordinary-fetch or loopback production fallback exists. The shipped deploy.json declares no egress binding; docs/ALERT-WEBHOOKS.md gives the `services` entry to add after installing it. Missing configuration is blocked visibly. Destinations remain scoped to projects, and uncertain sends never retry automatically. See [the signed payload, replay and privacy contract](docs/ALERT-WEBHOOKS.md).

The owner deploy declaration selects SendGrid, requires the destination and hash-key secrets, and installs the minute cron. Supply the existing mail API key and sender for that provider. The production build uses the same Worker-first asset routing as hosted deploy: public static assets go to `ASSETS`, while application documents and API handlers retain their own authorization. `pnpm test:alerts` includes native scheduled events against the emitted Worker and waits for a real complete minute of accepted spike events; local mail evidence is retrieved through the gated Base outbox. These local checks do not establish provider cron dispatch or recipient delivery.

Archives disable alert rules and quarantine historical delivery metadata. Active intents, spike cursors, Base integration queues, mail jobs and local outbox are excluded; restoring never resends old alerts. Reconnect destination configuration and enable a new rule revision for subsequent captures.

## First project and sign-in destination

The product installer requests ordinary owner sign-in with returnTo `/setup`. Its successful exit means the owner was claimed and its temporary runtime stopped; a fresh installation still needs its first project. The ordinary sign-in form defaults to `/setup`, including sent/failed redisplay, and preserves explicit safe local deep links. Confirmation keeps the destination stored when the link was issued. Spool mounts its product project-creation gate, not the retained Base owner-confirmation form in `src/base/setup.ts`; that inherited form and its `/signin` path do not define the public product flow.

After native owner authentication, document requests from an installation without projects redirect to `/setup`. That page creates a project through the existing same-origin owner `POST /api/projects` transaction and retains the once-shown ingest key only in memory, with copy and explicit Continue actions. Failed requests leave a usable form; when a response is lost, reload to check durable state before retrying. Losing the shown key does not undo the project: generate a replacement in Settings.

At least one durable project completes first run. Existing and ordinarily restored projects count immediately, including after a runtime restart; an empty restore/reset does not count. Completed `/setup` requests return a finite 303 to `/`; `/app` retains its redirect to `/`. Re-running setup preserves project data and cannot manufacture completion. Health, auth, local outbox, static assets and authenticated APIs remain available independently of this document gate, including empty project listing, archive and restore. To restore an archive before the first project, stop the runtime and use the existing import command above.
