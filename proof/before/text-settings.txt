Release recurrence

After resolving in the current release or an already observed named release, another event in that release increases the count and appears in the issue history. By default the issue stays resolved. A later release reopens it under the project release ordering rule.

 Reopen resolutions on another event in the same release

Applies to future accepted events. Older releases and events without a release keep their existing behavior. Plain Resolve still reopens on the next event. Next-release resolution waits above its boundary; a future named release reopens on its first event, and a later release still reopens it. Capture suppression still prevents reopening.

Sentry release identity

Sentry events can arrive without a release or automatically create one. Native v1 still requires a registered release and build. An omitted dist has a separate no-dist identity; an explicit dist is kept distinct.

Release ordering rule
First seen (default)
First seen
Semantic versions, then other names
Registered sequence only

First seen orders every release by its original first-seen time, then UTF-8 release name. Semantic order ranks all semantic versions first by precedence (build metadata is ignored), then non-semantic names by first seen. Ties use first seen and UTF-8 release name. Lists, latest and regression share this order. Registered sequence only refuses missing or unregistered releases and builds with a counted reason. Plain Resolve reopens on the next accepted event under either rule. Next-release resolution waits for a release later than the latest at resolution time; named-release resolution waits for the chosen release or a later one. Older and release-less events do not reopen either.

Automatic release name pattern

Only * is a wildcard. Unseen names outside the pattern are accepted as release none, with a processing note. Invalid names also become none. Existing releases stay available.
