# Spool handover

## Product and source

Spool is a local-first JavaScript, Python and Go evidence product with one owner and multiple isolated projects. `src/**` is authoritative. Keep the package, seed, repository, edition/source identities and lowercase API/asset paths stable. The lifecycle comes from the pinned `@runeditrun/rer` package (package.json). Base operator-auth, owner-claim, erasure, mail, portability and the other copied modules keep the adoption pins recorded in [base-copies.json](base-copies.json); retained source and copy records describe that adoption. Refresh Base only through `node scripts/edition-authoring/cli.mjs refresh-base` (then `verify-base` and `pnpm source:lock`); never regenerate application code over `src/**`.

The public `rer` lifecycle (`rer install`, `rer setup`, `rer dev`, `rer verify`, `rer reset`, `rer export`, `rer import`, `rer deploy --dry-run`) installs, sets up, serves, verifies, resets and transfers local data. Setup claims or preserves one real owner through native operator-auth, requests ordinary sign-in in the loopback outbox and stops its temporary app. Dev reports ready after health succeeds and stays in the foreground. Dev opens the native owner through the private checkout key by default; `--login` uses ordinary outbox sign-in. The outbox requires that key as well as loopback/request checks. Setup, dev, verify and deploy dry run do not provision remote resources.

The product stores scrubbed D1 events with bounded private source maps, grouping, revision-aware triage, project browser-origin policy, Base portability with native v1/v2 compatibility and manual retention. Owner sessions, ingest keys, read-only agent grants and release/map-only deploy keys have separate authority. Every private handler rechecks native owner or exact project authority directly; preserve the auth, origin, secrets and dispatcher boundaries in [AGENTS.md](AGENTS.md).

Alerts record new issues, later-release regressions and server-received window spikes with rules and delivery logs. The scheduled Worker evaluates windows and dispatches persisted delivery jobs. Base Mail requires provider acceptance. HMAC webhooks leave only through the `INTEGRATION_EGRESS` binding to a separately installed enforcing egress service; there is no ordinary-fetch fallback. Base's egress service is copied at `src/modules/egress-service` (its own Worker); the shipped deploy.json declares no binding, so webhooks stay off until the owner installs that service and adds the `services` entry in docs/ALERT-WEBHOOKS.md.

Supported Sentry exception envelopes/store intake share native admission and scrubbing; unsupported telemetry is counted and discarded. Bounded OTLP/HTTP JSON logs arrive at `/api/otlp/{project}/v1/logs` under the same ingest grant ([OTLP-INTAKE.md](docs/OTLP-INTAKE.md)). Native and Sentry intake also accept Python and Go exceptions, structured or parsed from text, with reported source paths; maps, the SDK and the reproducer stay JavaScript-only ([SUPPORTED-LANGUAGES.md](docs/SUPPORTED-LANGUAGES.md)). The SDK is published on npm as `@just-every/spool` (browser, Node, Workers, the `spool-sourcemaps` CLI and the Rollup/Vite plugin, which uses a project deploy key only for release registration and map upload); `packages/sdk` holds 0.2.0 (`client` and `exposure`) ready for the owner's `sdk-v0.2.0` tag, which `.github/workflows/sdk-release.yml` publishes after checking the version, CHANGELOG heading, main ancestry and a green Verify. Sentry organization imports run through Base import-kit's import door, vendored verbatim at rer-v0.2.72 with no local divergence in import-kit or the door, one pipeline for the owner's importer and Business grants (reviewed dry run, apply, reconcile, guarded undo, one history, and Business's tool archive with its restore check); Business reads the DSN switch through the signed, read-only, counts-only `POST /api/rer/cutover-status` ([SENTRY-SWITCHING.md](docs/SENTRY-SWITCHING.md)); qualification is synthetic-fixture-only until a real owner export passes and is reconciled. The homepage says Spool is a 100% free, open source alternative to Sentry, Bugsnag and Rollbar, naming them only as what it replaces (owner decision, 12 Oct 2026); no feature-parity or completed-migration claim is made.

Owners can correct grouping on exact retained occurrences: split and merge previews, revision-fenced apply and undo with the original grouping kept as provenance, operator-label assignment, literal suppression and deployment manifests ([OPERATOR-CORRECTIONS.md](docs/OPERATOR-CORRECTIONS.md)). Future capture keeps the default grouping, and a corrected issue carries a `grouping_changed` gap in repair observation.

Every issue has a stable short ID (`CHECKOUT-1A3`) that survives merge and split as an alias and is accepted wherever an issue is named. Deploy-key release and deployment registrations may carry each commit's message and author; `Fixes`, `Resolves` or `Closes` before a short ID links the commit to that issue at once and resolves it in the first release that includes the commit, while unknown, other-project and imported-history citations go to the owner's repository link log. Commit author and message stay owner-only unless the owner shares them per project ([SHORT-IDS.md](docs/SHORT-IDS.md)).

Reproduce, fix and measure: a source-mapped failure becomes a reproducer that `pnpm reproduce` runs in a workerd sandbox; with an owner-installed GitHub connection a grant-bound fix workflow opens a branch and draft pull request, and exposure reports from the SDK give a fix verdict. Spool never merges, releases or deploys ([REPRODUCE-AND-FIX.md](docs/REPRODUCE-AND-FIX.md)).

Managed producer/package/setup metadata, additive durable one-owner claim and optional native-owner-gated editor are implemented source. Editor configuration cannot be authorized by a project grant. The operations check covers source and generated local inputs; hosted installation and edit-to-source acceptance remain separate.

## Data custody and owner boundary

Setup preserves the owner and domain data, applies additive migrations and refuses ambiguous legacy state. Recovery requires a private full-database copy with the original configuration and migration ledger; a domain archive excludes credentials. Archives include private maps and browser-origin policy but exclude owner sessions and grants. Restore requires an empty destination and creates neither owner nor grants. Retention remains manual and preserves its visible cutoff, occurrence tombstones and deduplication horizon. Follow [OPERATIONS.md](OPERATIONS.md) before resetting or transferring evidence.

BASE-DATA-003 project erasure is implemented at `c279cd2d1fc02acfbc1160201782935e5324ddef` (GitHub Verify run 38215335300) on Base main's erasure helper (see docs/PROJECT-ERASURE.md): an owner-only route and Settings panel with a count-only preview, typed confirmation and a counts-and-times receipt; one fenced cascade over every project table, anonymised audit, restore fences and the 300-second cap are proven by `test:project-erasure` in verify. Every helper file, `src/modules/erasure/plan.mjs` included, is a byte-identical copy record of Base main. Retention remains separate and does not erase a project.

Installation-owner erasure ([OWNER-ERASURE.md](docs/OWNER-ERASURE.md)) hands the installation to a verified successor in one atomic step, then deletes, retires or replaces the predecessor's personal data with explicit holds; every owner write admitted before the handoff is refused afterwards, and pre-erasure archives are refused by the same restore fence.

The owner retains Sentry credentials and real export reconciliation, live accounts and mail sender configuration, provider/deploy calls, npm/public visibility changes, repository rename, tags, installation receipts and paid calls. Local deploy dry run makes no provider request. Those external actions require their own authorization and evidence.
