# Search and export retained issues

The Issues view searches every retained issue in the selected project. Combine words and fields such as `environment:production error.type:TypeError function:checkout after:2026-01-01`. Quote values with spaces. `before:` is exclusive and `after:` inclusive, using occurrence receipt timestamps; include an explicit timezone when specifying a time. `release:latest` means the newest registered sequence. Unsupported fields fail with a named error. All event conditions must match the same occurrence. An issue's occurrence count remains its full retained count.

`GET /api/projects/:project/issue-search` accepts `q`, `status` (all/open/acknowledged/resolved/suppressed), `release`, `sort` (priority/latest/occurrences), and `cursor`. It returns version 1, 25 rows, total matching issues, query-wide status/release/environment facets, and `next`. Priority sorts active regressions before new issues; ties use latest receipt and issue ID descending. Pass `next` unchanged as the cursor for the same query. Cursor pages observe current retained data; new intake or triage can move issues, so refresh to start a new traversal.

`GET /api/projects/:project/issue-export` accepts the same filters and `format=json|csv`. It streams all matching retained issue aggregates in batches of at most 100, without a total issue-count refusal. JSON states its initial matched `total`, final `exported` count and `bounds` (`batchSize: 100`, `limit: null`, `complete: true`). Intake and triage can move records during delivery; use a settled query window to reconcile counts. Revocation, removal, project erasure or a change to commit-sharing policy aborts delivery before the next batch. An interrupted JSON stream is incomplete and must be discarded; CSV consumers must treat a transport failure as incomplete. Exports do not contain occurrence payloads or attachments. Both doors require the current owner or an exact-project, current read-only agent grant; a shared search link never grants access.

Copy search link preserves filters and ordering. Viewing/unseen remains local to the browser and is shown for the current page, separate from server query-wide counts. Identity, custom-tag and collaborative search are still listed as gaps in CONTRACT.md.

## Version-1 occurrence and feedback reads

`GET /api/projects/:project/occurrences` lists retained occurrence metadata across the project. `GET /api/projects/:project/issues/:issue/occurrences` scopes it to one issue. Both accept the existing event query `q`, `order=newest|oldest` (default newest), and `cursor`. The version-1 response has `project`, `rows`, `total`, `next`, `bounds.pageSize` (25), `order` and `coverage`. Each occurrence row contains `id`, `occurrence`, `issue`, `received`, `release`, `build`, `environment`, `type` and `message`. These are already scrubbed retained values; the door excludes source context, local variables, user identity and attachments.

`GET /api/projects/:project/feedback-reports` has the same response envelope and ordering/cursor rules, with optional `issue` and no event query. Each row is `id`, `message`, `received`, `eventId`, `issueId` and `association` (`attached`, `event_unavailable` or `standalone`). It exposes scrubbed descriptions and exact-occurrence association only. Withdrawal removes the report from the next read.

All three doors require the owner session or a current read-only agent/service grant for exactly that project. Foreign-project grants, deploy grants and ingest keys receive the same 401 refusal before reading project records. Owner writes and the feedback inbox retain their existing owner authority. Invalid cursors, changed query/order or unsupported filters return 400; an authorized missing project/issue returns 404. The limit is 25 rows per page, using receipt timestamp and ID as a stable tie-breaker in the selected direction. Pass `next` unchanged to the same door/query. Totals cover the current retained matching corpus; pages are not snapshots, so refresh after intake, retention or withdrawal. Erasure removes the project and retires its grants.

Attachment and native-device qualification, complete whole-project exports and archives at GOV-003 volume, and the 160,000-event acceptance remain incomplete. The bounded attachment store below is an additive migration; the other record reads add no storage.

### Observed session report

SDK-005 adds the bounded version-1 `/api/projects/:project/release-health` read door and matching JSON download under the same owner-session or exact-project grant authority. It reports aggregate observed health and uncertainty, not a paginated session-record or release-record API. See [session report shapes and denominators](SENTRY-SESSIONS.md#read-and-export). The retained record doors below complement this report; they do not replace its observed health and uncertainty calculations.


## Version-1 release and session records

`GET /api/projects/:project/release-records` paginates retained release registrations. It accepts exact `release` and `build` filters, `order=newest|oldest` (default newest), and `cursor`. Each row contains `project`, `name`, `seq`, `build` and `created`, matching the core registration in the owner release list and private archive. Ordering uses `created` then the release name in binary order, both in the requested direction. The existing `/api/projects/:project/releases` interface keeps its array response, release policy ordering and supplementary metadata.

`GET /api/projects/:project/session-records` paginates retained individual session observations and aggregate status buckets together. Optional exact `release` and `environment` filters, `kind=all|individual|aggregate` (default all), inclusive `from` and exclusive `to` in integer Unix milliseconds, `order=newest|oldest` (default newest), and `cursor` select the corpus. Without a time filter it lists all retained observations. If both times are supplied, `to` must exceed `from`. Release and build filters are bounded to 200 characters; environment is bounded to 100; control characters are refused. Unknown or repeated parameters are refused.

Session rows contain `id`, `kind`, `sid`, `release`, `environment`, `started`, `updated`, `status`, `errors` and `quantity`. An individual row represents the current observation for one SID, with quantity 1. An aggregate row represents one retained release, environment, start-minute and status bucket; its SID, updated time and individual error count are null. Its quantity counts sessions, not individual identities. The opaque record ID encodes the retained row identity, distinct from any user identity. Ordering uses `started` then the record ID in binary order, both in the requested direction. No raw DID, keyed user hash or private project identity key is returned. Aggregate replay can increase quantities because the SDK supplies no aggregate capture ID; this door makes no new deduplication guarantee.

Both doors return `version: 1`, `project`, `rows`, `total`, `next`, `bounds.pageSize: 25`, `order`, `filters` and `coverage`. Session `total` counts individual observations plus aggregate buckets; `quantities.individualSessions`, `quantities.aggregateSessions` and `quantities.sessionsSeen` count observed sessions over the whole matching corpus. For a matching time window and environment these reconcile with the health report, while the individual records and aggregate buckets reconcile with the private archive. An empty corpus returns no rows and a null next cursor.

Each cursor binds its surface, project, filters and ordering, with a stable tie-breaker even when every timestamp is identical. Pass `next` unchanged and repeat the same filters. Cursors are limited to 4,096 encoded characters; malformed, empty, cross-surface, foreign-project and changed-query cursors return 400. A cursor is a position in current retained data, not a snapshot or authority: new intake, SID updates, retention and erasure are visible on the next read. Restart traversal to refresh. The existing 90-day session intake window, 50,000 individual observations and 10,000 aggregate buckets per project remain the storage bounds; pagination adds no retained-count refusal.

The current owner, an authorized project member, or a current exact-project read-only agent or service grant may read these doors. A foreign, ingest, deploy, invalid or revoked bearer gets the same 401 response and cannot borrow an owner cookie. Project erasure retires the grant and removes the records; an authorized missing project returns 404. Both responses are non-cacheable. Version 1 preserves the existing occurrence, feedback, release-list and health-report responses; these new routes add separate envelopes rather than change those response shapes.

## Version-1 project audit records

`GET /api/projects/:project/audit-records` returns the existing privacy-safe audit facts attributed to the current project alias. The current owner, permitted project member, or current exact-project read-only agent or service grant may read it. Ingest, deploy, foreign and revoked grants cannot read it, including when a request also carries an owner cookie. The organization audit keeps its existing authority and response.

The version-1 envelope contains `project`, `rows`, `total`, `highWater`, `next`, `bounds.pageSize: 25`, `order`, `filters` and `coverage`. Rows use the organization audit projection: sequence, permanent fact ID, creation time, source, safe actor and subject aliases, action, project alias, outcome and HTTP status. No attribution lookup, credential, concrete route, input or captured personal value is returned. Facts for other projects and installation-wide actions are excluded.

Optional `action` and `outcome` filters accept the existing named audit values; `order=newest|oldest` defaults to newest. Ordering uses the unique sequence. The first page fixes `highWater`; subsequent pages observe only facts at or below it, even as reading appends audit facts. Refresh to see newer facts. Cursors have the existing 4,096-character bound and bind the project alias, filters, ordering and surface. Malformed, repeated, unknown and changed-query parameters return 400. Pages are non-cacheable.

Erasure retires the project grant and deletes its attribution links; the safe permanent chronology remains in the organization audit. A private restore also preserves permanent facts without restoring private attribution links. Detached historical facts therefore remain in the organization audit, rather than being silently reassigned to a restored project's new alias. This boundary is separate from audit pagination and is not a claim of native-device attachment qualification or GOV-003 scale.

## Stream occurrence metadata

`GET /api/projects/:project/occurrence-export` exports the same safe metadata rows as the occurrence record API, in JSON (default) or CSV. Optional `q`, exact `issue`, and `order=newest|oldest` select the retained corpus. Unknown or repeated parameters are refused. The existing query language and its privacy restrictions apply. Source context, local variables, user identity and attachment bytes are excluded; this is not a private archive or a complete raw-event export.

The JSON envelope includes `version: 1`, `project`, `query`, `order`, initial matching `total`, `rows`, final `exported`, `bounds` and `coverage`. `bounds.batchSize` is 100, `limit` is null and `complete` is true for a completed traversal. Receipt time and binary event ID order break ties. CSV uses the same metadata columns, with formula-leading captured values made inert. No total-record cap is added. Batches observe current retained data; use a settled window and compare `total` with `exported` for reconciliation.

The owner, permitted project members and current exact-project read-only grants use the same metadata projection. Authority and project existence are rechecked before each batch leaves storage. Revocation or erasure aborts delivery. Audit records distinguish started, succeeded, failed and uncertain delivery; a request's 200 status alone is not proof that a stream completed. Private archives retain their existing integrity and inert-restore rules and their existing GOV-003 volume gap.

## Private attachment capture and reads

Attachment capture is disabled by default. The installation owner may inspect `/api/projects/:project/attachment-policy` and explicitly approve retaining private original bytes by PUT with the current `revision`, `enabled: true` and `confirm: "retain private original bytes"`. Configuration belongs to the project's Settings context; this round provides the API, without adding a new workbench control. A stale revision or missing approval is refused. Read grants cannot change the policy. Disabling it stops new capture; retained files remain under project authority until withdrawal, retention or erasure.

This is an interim owner-only custody default under the fleet's standing scope policy, not a completed SDK-003 scrubber or native-device qualification. Original binary bytes can contain personal information. Binary content is not scrubbed, and installation-owner self-erasure conservatively refuses while attribution of retained attachment content is unavailable. Do not enable capture for sensitive content without the installation's approval. These obligations remain in API-001's Gap.

After approval, Sentry envelope attachment items bind to the exact retained event occurrence named by the envelope. Missing parents never create orphan attachments; foreign or revoked ingest grants cannot store bytes. Each item is bounded to 256 KiB, each project to 1,000 files and 16 MiB; the existing 1 MiB expanded envelope bound still applies. These are implementation limits, below SDK-011's broader target. Responses name `attachment_stored`, `attachment_duplicate`, `attachment_disabled`, `attachment_invalid`, `attachment_oversized`, `attachment_capacity`, `attachment_event_unavailable` or `attachment_withdrawn`. A disabled store also retains the existing `sentry_unsupported_attachment` count. Attachment refusals preserve companion errors.

`GET /api/projects/:project/attachments` returns version-1 metadata pages of 25 rows, with optional exact `event`, `order=newest|oldest` and query-bound `cursor`. Rows name the attachment ID, exact event and occurrence, scrubbed filename, SDK attachment type, content type, byte length, SHA-256 and receipt time. Original bytes are absent. Ordering uses receipt time and binary attachment ID, with current-data cursor semantics and the same 4,096-character cursor bound as the other records.

`GET /api/projects/:project/attachments/:attachment/content` serves exact bytes only to a permitted project member, the owner, or a current exact-project read-only grant. PNG and JPEG images with matching signatures may open inline; `download=1` requests a download. Other content always downloads as an octet stream. Responses are non-cacheable, prevent MIME sniffing and use a sandboxed content policy. Every view and download, including a refusal, records a privacy-safe audit fact. No attachment URL supplies authority.

The owner may DELETE `/api/projects/:project/attachments/:attachment`. Withdrawal writes a portability tombstone and invalidates staged transfers; replay cannot restore that attachment identity. Retention removes files with their exact parent event, and project erasure removes files and capture policy with the project's journal. Private archives preserve IDs, bytes, digests and event associations, while capture approval and active grants never revive on restore. Downloaded copies require separate removal; an empty destination needs a later erasure journal to refuse an older archive. iOS and Android `attachScreenshot`, large view hierarchies, minidump processing, binary scrubbing, selective personal erasure and GOV-003 volume remain unproved.
