# Search and export retained issues

The Issues view searches every retained issue in the selected project. Combine words and fields such as `environment:production error.type:TypeError function:checkout after:2026-01-01`. Quote values with spaces. `before:` is exclusive and `after:` inclusive, using occurrence receipt timestamps; include an explicit timezone when specifying a time. `release:latest` means the newest registered sequence. Unsupported fields fail with a named error. All event conditions must match the same occurrence. An issue's occurrence count remains its full retained count.

`GET /api/projects/:project/issue-search` accepts `q`, `status` (all/open/acknowledged/resolved/suppressed), `release`, `sort` (priority/latest/occurrences), and `cursor`. It returns version 1, 25 rows, total matching issues, query-wide status/release/environment facets, and `next`. Priority sorts active regressions before new issues; ties use latest receipt and issue ID descending. Pass `next` unchanged as the cursor for the same query. Cursor pages observe current retained data; new intake or triage can move issues, so refresh to start a new traversal.

`GET /api/projects/:project/issue-export` accepts the same filters and `format=json|csv`. It exports all matching issue aggregates up to 10,000; a larger query returns 413 with its matched count and limit before sending a partial file. Paginate the API for larger results. JSON states its completeness and bounds. Exports do not contain occurrence payloads or attachments. Both doors require the current owner or an exact-project, current read-only agent grant; a shared search link never grants access.

Copy search link preserves filters and ordering. Viewing/unseen remains local to the browser and is shown for the current page, separate from server query-wide counts. Identity, custom-tag and collaborative search are still listed as gaps in CONTRACT.md.

## Version-1 occurrence and feedback reads

`GET /api/projects/:project/occurrences` lists retained occurrence metadata across the project. `GET /api/projects/:project/issues/:issue/occurrences` scopes it to one issue. Both accept the existing event query `q`, `order=newest|oldest` (default newest), and `cursor`. The version-1 response has `project`, `rows`, `total`, `next`, `bounds.pageSize` (25), `order` and `coverage`. Each occurrence row contains `id`, `occurrence`, `issue`, `received`, `release`, `build`, `environment`, `type` and `message`. These are already scrubbed retained values; the door excludes source context, local variables, user identity and attachments.

`GET /api/projects/:project/feedback-reports` has the same response envelope and ordering/cursor rules, with optional `issue` and no event query. Each row is `id`, `message`, `received`, `eventId`, `issueId` and `association` (`attached`, `event_unavailable` or `standalone`). It exposes scrubbed descriptions and exact-occurrence association only. Withdrawal removes the report from the next read.

All three doors require the owner session or a current read-only agent/service grant for exactly that project. Foreign-project grants, deploy grants and ingest keys receive the same 401 refusal before reading project records. Owner writes and the feedback inbox retain their existing owner authority. Invalid cursors, changed query/order or unsupported filters return 400; an authorized missing project/issue returns 404. The limit is 25 rows per page, using receipt timestamp and ID as a stable tie-breaker in the selected direction. Pass `next` unchanged to the same door/query. Totals cover the current retained matching corpus; pages are not snapshots, so refresh after intake, retention or withdrawal. Erasure removes the project and retires its grants.

Attachments and viewing audit/downloads, release/session and audit APIs, streaming exports/archives and the 160,000-event acceptance remain unqualified. These read doors add no storage or schema migration.

### Observed session report

SDK-005 adds the bounded version-1 `/api/projects/:project/release-health` read door and matching JSON download under the same owner/exact-project read authority. It reports aggregate observed health and uncertainty, not a paginated session-record or release-record API. See [session report shapes and denominators](SENTRY-SESSIONS.md#read-and-export). General release/session record pagination remains an API-001 gap.

### Retained issue impact

`GET /api/projects/:project/issues/:issue/impact` is a current human-session read. It independently enforces the existing project membership scope and does not expand agent packet authority. The version-1 response includes all retained event totals, first and last receipts, the shared SDK-008 affected-user definition and missing-user quantity, the last 24 hours' receipt rate, and ordered release history. Events without a release contribute to issue totals and are excluded and counted beside release history. Project release health remains a separately labelled 90-day cohort with SDK-005's original denominator notes.

An SDK may explicitly send its individual session identifier as `contexts.session.sid`. Admission retains a validated telemetry reference privately in the existing event record while ordinary session context stays redacted. Agent packets exclude the private reference. The impact read verifies that identifier against a retained individual session in the same project and environment, and the same release when the event names one. A release-less event can link to its explicitly named session but remains excluded from issue release-scoped figures. Distinct matching identifiers count once, even across repeated events. Session identities never populate event user identity. Missing, malformed, foreign, mismatched or expired session references remain unlinked; if any retained event is unlinked, the affected-session total is unavailable and the verified quantity is shown only as a lower bound. No association is inferred from a common user, release or network address. The qualified unmodified Python program does not send such an identifier automatically; its affected-session total remains unavailable. Aggregate session buckets cannot establish an individual association.

Retention changes these figures on the next read and exposes the project's applied cutoff and removed-event quantity. An issue with no retained events has no retained first or last receipt. Project erasure removes the read and retires the ingest authority; the private reference follows its event through existing archive, retention and erasure paths.
