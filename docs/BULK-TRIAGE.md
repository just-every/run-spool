# Bulk triage

Search the retained issue corpus, select individual rows or Select this page, choose an action, then Preview triage. Inspect the complete selection before applying. Changing filters or pages clears selection; this never selects unseen result pages. A current project member can acknowledge, reopen, resolve, archive, assign a member or merge the selection. Read-only collaborators can inspect issues but cannot apply these decisions.

Assignment accepts the same accessible member handles as discussion mentions. An unknown, ambiguous, removed or inaccessible handle is refused. A blank handle clears the assignment. The stored assignee is a safe member alias; the current name is shown while its attribution link exists. Assignment grants no access and sends no notification. TEAM-002 owns automatic ownership rules and TEAM-005 owns notification delivery.

Merge requires a target from the selected issues and previews the exact retained event moves and issue counts. It supports at most 200 retained events in one correction, preserves original grouping provenance and redirects every absorbed short ID to the survivor. A maintainer can undo the reviewed correction from the issue's existing Operator decisions panel; undo restores every original alias. Future captures keep their original grouping. Imported history is excluded.

Resolve supports plain, current, next and named-release modes through the shared release ordering rule. Plain Resolve reopens on the next accepted event. By default, next-release resolution waits for a release strictly above the frozen latest release. Repeats in that frozen release are counted on the shared timeline. Settings offers a previewed and audited same-release reopening policy for current and already observed named releases; it affects future accepted events only. Next-release resolution keeps SDK-009's strictly-later rule even when this setting is enabled. TEAM-003's conflicting next-release reopening sentence remains unqualified. Older-release repeats stay separately visible and cannot fabricate a newer-release regression. Events without a release retain SDK-009's behavior.

Archive supports a reason and forever, expiry, additional occurrences, affected users, shown historical forecast or snooze conditions. An expired condition reopens the issue once and creates one accountable follow-up. Restored history remains inert.

`POST /api/projects/:project/bulk-triage` accepts `issues: [{id, revision}]` and `apply: false`. State actions use `state` (`open`, `acknowledged`, `resolved`, `suppressed`); resolution and suppression use their single-issue inputs. Assignment uses `action: "assign"` and `member` (a handle or null). Merge uses `action: "merge"` and `target` (a selected issue ID). Apply sends the same selection and action with `apply: true` and the returned `preview`. Between 1 and 100 unique issues are supported, with at least two for merge.

Preview moves no retained occurrence or aggregate. Merge stores an inert correction preview. Apply fences every selected revision, merge occurrence and assignee authority before changing any row, and commits the whole selection with its audit in one authorized batch. A stale selection, changed action, wrong project or revoked authority refuses the operation. Refresh and select again after a conflict. Project grants cannot authorize bulk writes.

The existing private archive and project and owner erasure paths cover the unchanged assignment, correction, activity and triage stores. Archived aliases confer no membership and do not restore notification authority.
