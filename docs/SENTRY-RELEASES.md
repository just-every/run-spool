# Sentry release identity

Sentry events need no release-registration step by default. A release-less event is stored with an empty release identity, displayed as **none**, counted in Issues and searchable with `!has:release`. It creates no synthetic release record. Release history excludes it and shows the retained count without a release. Native v1 intake still requires a registered release and exact build.

The first accepted Sentry error carrying a new release creates it atomically with the occurrence, grouping aggregate and alert. Filtering, duplicate checks and admission budgets run first. A release records its first-seen time, first environment and sanitized SDK metadata. The release history labels it Auto-created. An absent dist uses its own `sentry-no-dist` identity; another explicit dist is recorded separately. Registering the same release through the native release API enriches it and removes the auto-created label without changing the original sequence or first-seen data. Source maps retain exact release/build/debug identity.

Invalid names (empty, `.`, `..`, `latest`, control characters, slash, backslash or more than 200 characters) become none, with an invalid-release processing note and counted outcome. A project can restrict automatic creation with a literal pattern where only `*` is a wildcard. An unseen name outside the pattern becomes none with a separate note/outcome; an existing release stays available. Retries still compare the canonical original SDK JSON digest, before these processing decisions.

In Settings, **Sentry release identity** shows the active ordering rule. Two supported semantic release names compare major/minor/patch, prerelease and numeric build. Other pairs compare their first-seen sequence. Changing the rule previews resolved-issue boundaries and applies to later intake, under a revision and owner-authority fence. **Registered sequence only** refuses missing releases as `missing_release_register_required` and unknown or auto-created release/build identities as `unregistered_release_or_build`, with the registration path and a project outcome.

In issue triage and bulk triage, **Plain · next accepted event** resolves independently of release. The next unsuppressed accepted event reopens it and produces one regression alert, including the same release or none. **In current release** protects older and same-release events under the ordering rule. An independent observed release boundary prevents a late older semantic version from moving that resolution backwards; the original numeric watermark remains intact for archive and repair coverage. Release-less repeats after a current-release resolution are counted and shown on the issue, without reopening it.

Private archives preserve release policies, metadata, dist identities and resolution boundaries, while old archives start the new tables empty. Project erasure includes every new table. Existing owner-erasure holds apply to structural identities and policy text; no stored credential or session is added to an archive.

This is partial SDK-009. Sessions are still diagnosed as unsupported. Next/named-release resolution, sentry-cli/build-plugin registration, linked-repository commit association, migration-wide count reconciliation, advanced release-based alert conditions, policy-driven `release:latest` and full Python/mobile/runtime qualification remain open. Mixed semantic/nonsemantic histories can make the target's pairwise ordering non-transitive; deterministic global latest/list semantics need the contract clarification requested from ct. Legacy release boundaries without new metadata retain their conservative registered-sequence behavior.
