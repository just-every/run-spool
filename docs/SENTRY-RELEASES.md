# Sentry release identity

Sentry events need no release-registration step by default. A release-less event is stored with an empty release identity, displayed as **none**, counted in Issues and searchable with `!has:release`. It creates no synthetic release record. Release history excludes it and shows the retained count without a release. Native v1 intake still requires a registered release and exact build.

The first accepted Sentry error carrying a new release creates it atomically with the occurrence, grouping aggregate and alert. Filtering, duplicate checks and admission budgets run first. A release records its first-seen time, first environment and sanitized SDK metadata. The release history labels it Auto-created. An absent dist uses a separate internal `[sentry:no-dist]` identity that SDK dist strings cannot use. An explicit `sentry-no-dist` stays distinct. Upgrade separates retained events and observed builds using their Sentry dist evidence; legacy registrations and artifacts whose intent cannot be recovered retain the original explicit identity. Registering the same release through the native release API enriches it and removes the auto-created label without changing the original sequence or first-seen data. Source maps retain exact release/build/debug identity.

Invalid names (empty, `.`, `..`, `latest`, control characters, slash, backslash or more than 200 characters) become none, with an invalid-release processing note and counted outcome. A project can restrict automatic creation with a literal pattern where only `*` is a wildcard. An unseen name outside the pattern becomes none with a separate note/outcome; an existing release stays available. Retries still compare the canonical original SDK JSON digest, before these processing decisions.

In Settings, **Sentry release identity** shows the active ordering rule. The default orders every release by original first-seen time, then UTF-8 release name. Optional semver orders all semantic versions before non-semver names; semantic precedence ignores build metadata, with ties broken by first-seen time and UTF-8 name. Non-semver names use first seen and UTF-8 name. Lists, latest search and regression use this same total order. Changing the rule previews resolved-issue boundaries and applies to later intake, under a revision and owner-authority fence. **Registered sequence only** refuses missing releases as `missing_release_register_required` and unknown or auto-created release/build identities as `unregistered_release_or_build`, with the registration path and a project outcome.

In issue triage and bulk triage, **Plain · next accepted event** resolves independently of release. The next unsuppressed accepted event reopens it and produces one regression alert, including the same release or none. **In current release** protects older and same-release events under the ordering rule. An independent observed release boundary prevents a late older semantic version from moving that resolution backwards; the original numeric watermark remains intact for archive and repair coverage. **In next release** freezes the latest project release under that order and reopens strictly above it. **In a named release** requires an existing release and reopens at that release or later. Release-less repeats after release resolution are counted and shown on the issue, without reopening it.

Private archives preserve release policies, metadata, dist identities and resolution boundaries, while old archives start the new tables empty. Project erasure includes every new table. Existing owner-erasure holds apply to structural identities and policy text; no stored credential or session is added to an archive.

SDK-009 covers the existing event release paths. Sessions inherit the same identity rules in SDK-005; SRC-003 inherits sentry-cli/build-plugin registration, SRC-002/TEAM-004 linked-repository commit association, MIG-001 migration reconciliation, ALERT-001 release-less alert conditions, SDK-001 full Python/mobile/runtime qualification, and ALERT-005 chat Resolve. These capabilities retain their own incomplete status and acceptance journeys. Existing derived version keys are upgraded without changing first-seen time. Native intake continues to use registered sequence.

Native deployment history records owner/deploy-key starts, progress, success, failure and rollback per environment. Supply an explicit deadline, an existing email destination and the ordered included commit SHAs; each may also be an object with its message and author, whose `Fixes`, `Resolves` or `Closes` citations link and resolve issues by short ID ([SHORT-IDS.md](SHORT-IDS.md)). Commit ancestry is caller recorded until SRC-002 supplies connected read-back; SRC-003 supplies unmodified CLI/plugin registration. Callback IDs are idempotent; changing their contents conflicts. A scheduled pass records an overdue start and makes one notice attempt, without inferring a deployment failure. Archives preserve history with callbacks and notifications disabled.
