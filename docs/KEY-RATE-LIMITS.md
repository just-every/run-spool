# Capture key event limits

An installation owner or organization admin can open Settings, find an active capture key under Project keys, open its Details and save an individual event limit per minute or hour. Other project roles and project credentials cannot configure these limits. Revoked, stopped, foreign and non-capture keys cannot be configured.

Each key has independent UTC minute and hour counters. A newly accepted native error or Sentry error spends one event in the same database transaction that stores its occurrence. Filtered events, duplicate retries, conflicting retries, invalid events and refused events spend none. Both counters run even while the individual limit is off. Changing the number, switching periods, disabling and re-enabling a limit, or restarting the installation preserves current usage. Reducing a limit below current usage blocks subsequent new events until the selected UTC period expires or the owner increases the limit. Increasing a limit permits only the additional unused allowance.

Exceeding the selected period returns HTTP 429 with reason `key_rate_limited`, integer `Retry-After` between one second and the selected period, and `X-Sentry-Rate-Limits` restricted to the `error` category. The installed SDK applies that backoff to its own DSN; a second key continues to ingest independently. A mixed envelope counts every key-limited error and still processes client reports and other supported categories. Capture receipts show these refusals separately from project rate limits and SDK-reported discards.

These controls apply to accepted errors only. They do not add commercial quota, USD forecasts, monthly budgets, baseline spike protection or sampling previews. Existing project limits still apply; GOV-003 retains their removal and published-rate obligations.

Key configuration changes produce safe permanent audit facts. Key-specific configuration and bounded counters stay with this installation's credentials and are excluded from private archives. Historical project refusal quantities remain in the archived outcomes. A restore creates neither credential authority nor live key quota state: create fresh keys and configure their limits after restoring. Project erasure deletes both quota tables. Personal owner erasure removes quota rows belonging to deleted credentials while keeping limits and usage for surviving project ingest keys, without an owner attribution link. A revoked or erased key cannot attribute usage or replay a capture.
