# Observed sessions and release health

Spool routes Sentry envelope `session` updates and `sessions` aggregates through the same DSN authentication, Origin/Referer and allowed-domain fences as error intake. Available transport, release and environment filters apply before storage; stack/message-specific filters have no session evidence. An item is bounded to 100 KiB. Each project accepts at most 1,200 session items per receipt minute, 50,000 individual session IDs and 10,000 aggregate status buckets. Capacity, rate, malformed, oversized, filtered, missing-release and strict-release refusals have separate counted outcomes. A refused session never creates an occurrence, issue, alert or accepted-error unit. A companion error retains its ordinary admission. When the project-minute bucket is exhausted, the successful envelope response includes `X-Sentry-Rate-Limits: <seconds>:session:project:session_rate_limited`. The integer interval is rounded up to the end of the receipt minute and is bounded to 1–60 seconds. It limits only the `session` category, which covers both individual and aggregate items; errors continue through ordinary admission. No global `Retry-After` is set for this refusal. Invalid and capacity refusals retain their own counted outcomes and do not advertise a temporary rate limit. The installed SDK discards captures during backoff and reports `ratelimit_backoff`; recovery admits a fresh capture, without replaying suppressed sessions.

An individual session is identified by its SDK `sid`, with its SDK start time, release and environment bound on first observation. Updates keep the latest timestamp, maximum error count and conservative terminal state; replaying an update does not add another session. Release-less sessions are counted as `session_missing_release`, not invented as healthy exposure. An unseen valid release is created with SDK-009's shared release policy and first-seen metadata; optional registered-only policy and automatic-name restrictions still apply. `init` and duration do not create extra exposure. Raw `did`, IP and user-agent fields are never stored. A session `did` is represented only by HMAC-SHA256 under a random project key, born in the intake transaction. The key travels only in the private archive and is removed by project or installation-owner erasure. Default ADOPTED: use a keyed hash for sessions until the SDK-008 identity-policy slice is available; no raw identity is enabled by this feature.

Server-mode aggregates retain only release, environment, SDK minute, status and quantity. They contain no user denominator. Each item has at most 100 aggregate entries; quantities are safe bounded integers, with at most one billion in a retained bucket. Since the SDK supplies no aggregate identity, repeated aggregate envelopes cannot be deduplicated; that uncertainty is explicit. Sessions older than 90 days are refused; expiry is applied on subsequent session intake. Automatic idle-project expiry and longer-volume retention qualification remain gaps.

## Read and export

`GET /api/projects/:project/release-health?from=<epoch-ms>&to=<epoch-ms>&environment=<optional>` is version 1. The window is positive and at most 90 days; it defaults to the last 24 hours. The owner or an exact-project read-only agent/service grant can read it. Foreign-project, deploy and ingest credentials receive the same sign-in refusal. `download=1` exports the same bounded JSON with a download disposition; no secret, raw identity or user hash appears in this report.

The response has `version`, `project`, `window`, `rows`, `denominators`, `outcomes`, `method` and `coverage`. Each release/environment row contains sessions, crashed, abnormal, unhandled, active and aggregate observations; known-user counts; crash-free session/user numerators and rates; observed session adoption share; and 95% Wilson score intervals. Zero exposure is unavailable, never inferred healthy. Crash-free conservatively excludes crashed, abnormal and browser-unhandled observations. Active `ok` means observed so far, not a completed healthy session. Anonymous individual sessions and server aggregates have unknown users and are excluded from the known-user denominator. Loss counts are receipt-minute, project-wide observations and cannot be attributed to a release/environment; client-discarded quantities remain separate from accepted errors.

The existing Releases page shows both older and newer releases over the same window. The issue's suspect comparison also shows these observed rates beside its receipt-window occurrence counts. Sampling, independence of observations, device adoption and comparable device/OS cohorts are not established by the Wilson intervals; they do not demonstrate release causality.

## SDK source and qualification

### Native Spool SDK

The packed JavaScript SDK in this checkout supports opt-in browser page and Node process sessions through `sessions: true`, and explicit `startSession(options)` boundaries in its browser, Node and Worker entries. The published npm 0.1.0 package does not contain these additions. `POST /api/ingest/:project/sessions` accepts one session observation, with the existing project ingest grant and Origin and Referer fences. It reuses Sentry session validation, filtering, release creation, keyed DID storage, refusal accounting, project-minute backpressure, archives and erasure. Session observations create no error occurrences or accepted-error units. Native attempts have safe `capture.native` audit facts.

Browser close and page exit finish a session; a back-forward-cache restoration starts another. A browser exception remains `unhandled`, distinct from a Node fatal process crash. Node's healthy `beforeExit` and bounded fatal exit retain their host semantics. Repeated terminal calls do not add sessions. Worker callers await an explicit boundary or keep it alive with their execution context. Sampling is opt-in configuration at the caller: rates remain observed proportions, with no claim of corrected population rates. Sampling, suppressed observations and unknown delivery are available through the separate `onSessionOutcome` callback; durable offline delivery, request aggregation and server-side client-loss reporting remain unqualified. Native sessions never add a device model or OS claim, and their optional random install identifier stays keyed in session custody.

`tests/sdk-package.mjs` invokes `tests/native-session-flow.mjs` nativeSessionFlow against the packed artifact installed into a fresh application. Node healthy, handled and fatal processes, opted-out and unsampled processes, browser healthy and unhandled sessions, an offline browser gap followed by a fresh observation, and the manual Worker entry reconcile with health and downloaded reports. The same journey checks grant refusals, available category filters, invalid and oversized observations, safe audit facts, private session custody and project erasure followed by a refused replay. Existing error assertions remain in the enclosing package journey.

The unmodified JavaScript 11.6.0 core serializes `sid`, `init`, `started`, `timestamp`, `status`, `errors`, `did`, duration and release/environment attributes in `@sentry/core/build/esm/session.js:86–104`; DID selection is id, email then username at lines 23–29. `envelope.js:23–31` selects `session` versus aggregate `sessions`. Default Node `@sentry/node/build/esm/integrations/processSession.js:7–14` starts a process session and ends a healthy one on `beforeExit`. Browser `@sentry/browser/build/npm/esm/prod/client.js:20` sets the unhandled session status to **unhandled**; it is distinct from the Node/core **crashed** status (`@sentry/core/build/esm/client.js:108,461–484`). Spool preserves that distinction; a JavaScript exception does not prove a browser process crash.

Pinned Python 2.72.0 source, read only: [session.py](https://github.com/getsentry/sentry-python/blob/2.72.0/sentry_sdk/session.py#L140) serializes individual sessions; [sessions.py](https://github.com/getsentry/sentry-python/blob/2.72.0/sentry_sdk/sessions.py#L203) aggregates terminal request sessions by release/environment/minute with no DID. Source reading alone is not Python release-health qualification.

`tests/sentry-sdk.mjs` [SDK-005] runs the same default Node process and browser program first against a reference collector and then against Spool with only DSN changed. Healthy, Node-crashed and browser-unhandled observations across two releases reconcile exactly; the release screen reflows at 1440 and 390 with no serious/critical Axe finding. `tests/session-flow.mjs` sessionFlow also invokes `tests/session-backpressure.mjs` sessionBackpressureFlow. It fills the project bucket through public intake, then uses the installed unmodified Node SDK transport and session capture APIs to prove category backoff, companion error admission, deadline recovery and exact refusal and client-discard quantities. Public aggregate intake reaches capacity independently; malformed items retain invalid outcomes. Invalid, revoked and foreign grants change neither project’s session or discard counters. The SDK clock is pinned while the Worker’s minute bucket uses real time. `tests/sdk-runtimes.mjs` reconciles each runtime's actually emitted session items as stored rather than unsupported; untouched categories keep their exact counts. Migration 0065, old-archive adaptation, private archive/restore and project/owner erasure retain custody without raw DID.

Remaining gaps: mobile modes and device, OS and version cohorts, ANR rates, rollback and comparable adoption cohorts, trends, a real 20% rollout acceptance, runtime-specific health qualification beyond Node and browser, native durable offline delivery and request aggregation and client-loss reporting, full SDK-008 policy and role scope, idle expiry and aggregate replay deduplication. Session-category backpressure is qualified by the journey above; other telemetry categories remain outside this session slice. The inherited SDK-005 sentence “sessions accept no release” remains unmet: this slice follows SDK-007 and the round brief by counting them invalid, and does not narrow that sentence. Unknown or revoked keys create no project records; an unauthenticated key refusal is not allowed to mutate a project's session counter. Loader disabled state is not an ingest-key disable policy; an additional independently disabled ingest-key state is not introduced here. No real provider, device or hosted account was used.
