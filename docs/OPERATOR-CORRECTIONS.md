# Operator corrections and deployment evidence

These are owner workbench operations, independently authorized by every route and fenced against owner handoff inside their D1 transaction. An agent, ingest or deploy key cannot assign, regroup or change a suppression policy. Cookie writes require the same origin. Deployment registration alone also accepts an exact-project deploy key.

## Grouping

An exact-project agent grant may submit one inert proposal with `POST /api/projects/:project/grouping-proposals` and read safe summaries with `GET` on that exact route. Each submission is bounded, scrubbed and attributed by the service as `proposed by agent <alias>`. The input compares stack/release/route variants with a rationale and received-time window, plus either a split's event IDs, a merge's target revision, or a versioned future-capture rule policy. Current source and relevant target/policy revisions fence the review. This exception grants no wider evidence access, operator identity or grouping authority; TEAM-001 roles are not implemented by these aliases.

Only the owner reads `GET .../grouping-proposals/:id` with its full explanation, affected occurrences, counterexamples and alert/rate/repair implications. The owner uses `POST .../:id/approve` or `POST .../:id/reject` with `{}` after review. Submitting a proposal changes no group, policy, alert, delivery or repair result. Approval is an explicit owner action; agent credentials cannot approve, reject, apply or undo. Use the existing correction/policy owner flows for the resulting change and preserved history. See [agent setup and proposal JSON](WITH-YOUR-AGENT.md#propose-a-grouping-correction).

The native anchor remains `js-frame-v1`: exception type and first generated file, function and line, excluding message, column and release. JavaScript bundle routing removes Vite’s default eight-character hash suffix and hexadecimal content-hash suffixes (8–64 characters) from the grouping key. Origin, directory, entry name, extension, function and line still distinguish groups. Reported frames and source-map coordinates stay unchanged. The stable key and its original anchor persist through retention and archive restore. For older issues with retained evidence, capture reconnects to the earliest matching native issue (first-seen time, then issue ID); it does not merge existing occurrence histories. An old issue with no retained grouping evidence cannot be reconstructed from its fingerprint alone. The independently labeled `tests/fixtures/grouping-labelled.json` records a correct default relation, a false merge from one minified line and a false split after a bundle changes. The public product flow admits its actual events, demonstrates those relations, and exercises correction and undo; it never reads expected issue hashes from the corpus.

`POST /api/projects/:project/corrections/preview` takes either `{kind:"split",source,revision,events:[eventId,...]}` or `{kind:"merge",source,revision,target,targetRevision}`. A preview stores exact occurrence identities, issue revisions and before/after counts, with every proposed move and the new issue ID for a split. It moves nothing and sends no alert. One current unapplied preview is kept per project; a new preview replaces it. The Issue view exposes selectable packet occurrences and an issue-ID merge target. The API can select up to 200 retained occurrences; a merge refuses if its source exceeds that bound. Imported history cannot be moved into live groups.

`POST /api/projects/:project/corrections/:id/apply` requires `{confirm:true}`. All reviewed issue revisions, counts and occurrence identities are checked within the same transaction that performs the moves. Stale preview, capture, triage, assignment or retention conflicts without a partial move. No payload, digest, diagnostic, occurrence identity or receipt timestamp is rewritten. An additive provenance row preserves the original algorithm, basis, fingerprint and issue. Packets show original grouping beside current issue and correction. A moved event retry remains a duplicate of its current issue.

Corrections affect **only the exact stored occurrences**. Future events follow the original deterministic grouping algorithm. Corrections create no accepted counters, alerts, delivery intents or delivery rows. Corrected occurrences are excluded from subsequent spike evaluation, including after undo, so historical operator work cannot create a new live volume signal. Existing alert history remains evidence of the admission-time group.

Apply and undo derive each affected issue's headline from its earliest retained member, or show that no occurrences remain. They do not carry a source headline into a split whose members never supplied that text. Historical alert titles stay tied to their original alert, rather than being replaced with a newer issue headline.

`POST .../:id/undo` also requires `{confirm:true}`. It returns only the original retained occurrence to its prior issue, with guards on all post-apply issue revisions and the occurrence's latest correction. Newer work, retention, an event-ID reuse, or a second correction causes refusal. Undo changes neither triage nor assignment and never recreates a deleted event. Empty issues remain inspectable. History is capped at 50 records per project; reaching that cap refuses a further correction rather than silently losing provenance or undo guards. Each record contains IDs and counts, never copies of event payloads.

Repair observation cannot improve because evidence moved away. A retained occurrence counts for its native admission group, its current group, and each group it occupied during the repair's lifetime, using correction audit times and exact occurrence keys. This preserves a witnessed recurrence through repeated splits, merges and undo without associating a reused event ID with old custody. Corrections made before a repair also matter: a corrected group has no matching future-capture rule. Every issue involved in an applied or undone correction therefore carries a `grouping_changed` coverage gap. A retained qualifying occurrence still gives `recurred`; otherwise the verdict is `inconclusive`. Undo restores membership but does not claim new coverage evidence. Unaffected issues can still show `no_recurrence_after_exercise` under the existing capture, map, exercise, loss and retention conditions.

## Assignment and suppression

`PATCH /api/projects/:project/issues/:issue/assignment` takes `{revision,label}`. The bounded scrubbed label (80 characters) records operator responsibility, and `null` unassigns. This is deliberately a label, not an invited person or extra account: the installation still has exactly one owner. It grants no access and sends no notification. Assignment, reassignment and unassignment increment the issue revision and write an audit entry.

`POST /api/projects/:project/suppression-policies` accepts `{field,mode,value,enabled}`; `PATCH .../:id` additionally requires `revision`. Each project has up to 20 policies. Fields are original `fingerprint`, `release`, and sanitized `message`; modes are case-sensitive `exact` and literal `substring` (fingerprints require exact). No regex executes. Values are scrubbed, nonempty and at most 160 characters. The Issue view exposes create and enable/disable controls, revisions and the operator audit.

Policy matching occurs in the admission transaction, using the accepted normalized event, so a policy change cannot race a previously computed decision. Matching events remain accepted, retained and counted, with a per-occurrence receipt naming matching policy IDs, revisions, fields, modes and values. They create no new/regression alert, intent or delivery and never contribute to spike windows. A matched occurrence does not consume later new-issue or regression eligibility, and leaves an otherwise resolved issue resolved; accepted distinct events still advance count and revision under the existing release-watermark semantics. Disabling or editing a policy does not unsuppress earlier receipts. Policies affect future admissions; they do not retract already queued alerts. Manual issue suppression retains its existing lifecycle semantics and spike exclusion.

Admission keeps at most two payload-free audit facts per native issue: tracking began at its creation, and a receipt-free occurrence has been accepted. The latter consumes new-issue eligibility even when manual suppression prevented an alert. Facts commit with admission, survive full or partial retention and travel in archives; they retain only the issue ID, kind and time, never a deleted event identity or diagnostic copy. Moving an occurrence does not reset its native issue's history. Policy-only history remains eligible after retention when tracking covers the issue's lifetime. Older archives remain accepted without these facts: retained receipt-free history or an earlier new-issue alert still consumes eligibility, while a retention gap during an untracked issue's lifetime makes missing history unknown and conservatively prevents a new-issue alert. Regrouping can rewrite first-seen time, so an untracked corrected issue conservatively treats any project retention gap as unknown history. Regression eligibility continues to use resolved state and release watermarks.

## Deployment manifests

The existing `POST /api/projects/:project/releases` accepts an optional `manifest` with all of:

```json
{"name":"web@2","build":"bundle-2","manifest":{"commitSha":"0123456789012345678901234567890123456789","repository":"https://example.test/team/repo","deployedAt":"2026-10-10T12:00:00.000Z","environment":"production"}}
```

The commit is a full lowercase 40- or 64-digit SHA. Repository URLs must be canonical HTTPS without userinfo, query or fragment; they are never fetched. Deployment time is a canonical ISO UTC timestamp. A `(project,release,environment)` binding is immutable: identical retries are idempotent and changed identity conflicts. A manifest may be added to an already registered release; another environment can have a separate binding. Register a distinct release identity for a second deployment of the same code to the same environment if its deployed-at time differs.

Packets and the Issue view show the first and last retained occurrence's exact release and environment and its matching manifest, ordered by receipt time then event ID. Unknown manifests are explicitly unknown. Registering manifests out of order cannot replace this event ordering, and a rollback's later event points to the older release's binding. Manifests are owner/deploy-key records, not independent provider deployment proof. Existing release registration sequence continues to control admission/build identity, regression and repair observation; this change does not silently redefine those contracts.

## Custody and boundaries

Operator tables and stable bundle grouping routes travel in native archives, with semantic validation of grouping provenance, correction plans, policy receipts, assignment scope and manifest URL/identity. Pre-change archives restore with these additive tables empty; unchanged events derive their original grouping from their retained payload. Project erasure declares every new table, removes its rows and anonymizes operator audit details. Retention cascades per-occurrence provenance and suppression receipts, preserves only bounded ID/count history, and invalidates undo through the existing issue revisions and occurrence checks.

Before removing an occurrence's provenance, retention follows its original, current and every applied or undone intermediate group in the same project. Alerts have no headline occurrence key, so their diagnostic headlines are withdrawn conservatively for those groups. Their intent bodies and local mail text are scrubbed, development outbox copies and immutable integration envelopes are removed, and pending delivery work is canceled. Safe delivery status and attempt chronology remain, with `retention_removed`; database guards prevent a previously started expansion from recreating a private copy. Current issue titles are rebuilt from their actual retained members inside the retention transaction. Unrelated projects and groups keep their diagnostics, while snapshots are invalidated and occurrence tombstones still fence old archives. Already delivered mail and external provider records are outside local retention.

Owner erasure refuses with an explicit unsupported-attribution hold if a known owner identifier appears in an assignment label, correction basis, policy value/receipt, manifest URL or operator audit. It does not silently drop attribution or rewrite an immutable record. Clearing a label alone does not remove its prior audit attribution; project erasure removes the complete project custody when appropriate. Other owner-erasure paths continue unchanged.

These are implemented flows with public HTTP/UI and semantic restore/erasure tests in the existing suites. Test execution and hosted/provider acceptance are separate evidence; source and a deployment record alone do not establish them.

Each project retains at most 50 proposals. Each request is at most 32 KiB, and an exact server-computed review snapshot is at most 2 MiB; proposals exceeding a bound are refused, never silently clipped. Snapshots remain inspectable after a decision and travel in private archives. Restoring them never applies their advice.
