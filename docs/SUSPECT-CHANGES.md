# Suspect changes and engineer judgments

An issue's **Suspect changes** section connects its first retained occurrence, latest 20 retained reactivation alerts and observed rate increases to recorded release commits and deployment windows. Each candidate names the occurrence, exact regression alert or matched-cohort contrast that established it. These are correlations; they never establish cause or repository ancestry. A release with no recorded commits has a release-only candidate. Retention and imported history can limit the available basis. At most 100 candidates are shown, with available counts stated.

Release and deployment registration accept optional `files` on an included commit: a list of at most 200 scrubbed relative repository paths, each at most 512 characters. Bare SHA receipts remain supported; absence of `files` means unknown, while an empty list records no changed files. The first recorded list is immutable: identical repeats are idempotent and a conflicting list refuses the whole registration. Traversal, absolute paths and secret-bearing paths are refused. Sentry release commit `patch_set` paths use the same rules. No repository or source content is fetched.

Source matching compares these caller-recorded paths with exact retained frame paths in that release. A mapped frame uses the original path recorded at admission; otherwise it uses the reported path. Only a leading `./` is normalized. No basename, suffix or ancestry is guessed. Each overlap names its retained event and frame, labelled as correlation; no overlap is an explicit result. Source reads use at most 100 recent issue events per release and expose at most 30 matches per candidate.

The owner or a permitted native project member can **Confirm suspect** or **Reject suspect**, with a scrubbed evidence note of 1–600 characters. The current revision fences conflicting decisions. Each successful judgment has one audited entry and changes no occurrence, count, grouping, alert or issue status. A rejected hypothesis remains visible with its evidence. The judgment records an engineer's assessment, not demonstrated cause.

The same section compares occurrence and distinct-issue counts per release over one receipt window (default 24 hours; bounded to 90 days). Older-release failures stay alongside the new release, including unrelated spikes. Release-less occurrences are excluded and counted. The existing SDK-005 session rates, user denominators, observed adoption and Wilson intervals remain beside them.

**Comparable cohorts and loss** groups individual sessions by the same environment, coarse device family and OS family over the requested window. Coarse families are derived from the session protocol's user agent; the raw user agent is discarded. Device families are desktop, mobile, tablet or unknown; OS families are Android, iOS, Windows, macOS, Linux or unknown. These observations do not qualify a native device or identify an installed device. Older sessions without this metadata and aggregate sessions stay explicitly unknown and cannot establish a comparable cohort. An issue event with missing device or OS dimensions withholds event-rate contrasts for its release and environment; unknown events are never assigned to known cohorts or treated as zero failures.

Within each cohort, adoption is each release's observed session share. Contrasts follow the project's release ordering and compare adjacent observed releases in that same cohort. They show this issue's events per observed session and the change in unhealthy-session proportions, with counts and 95% Wilson intervals. Events use receipt time; sessions use start time. Event frequency is not a probability and can exceed one; active sessions are incomplete. A positive issue-frequency change establishes a labelled rate-change candidate, not a demonstrated cause. At most 200 cohort rows and 100 contrasts are included; available counts and limits remain visible.

Project-wide receipt-minute loss counters and retention gaps accompany the comparison. They cannot be assigned to a release or cohort. Sampling, unseen clients and unreported loss remain unknown; matching coarse cohorts and a missing loss counter do not prove complete capture. Impact attribution is withheld. Actual device adoption and causal attribution are never inferred from these rates.

An explicitly requested, exact-project agent packet carries at most ten suspect candidates with bounded reason records, deployment windows, matched paths and scrubbed engineer judgments. Its comparison window ends at the issue's last receipt, keeping settled packet reads reproducible. Commit authors, unmatched paths, operator identities, source content and raw user agents are excluded. Rejected hypotheses stay visible as known false positives for later AI-006 work. This records evidence for later learning; automatic model calls, patches, outbound delivery and grant expansion are not performed. Any later agent action remains a call governed by the company's policy under AI-006.

HTTP: `GET /api/projects/:project/suspects/issues/:issue` accepts millisecond `from` and exclusive `to`; `PUT` on the same path accepts `release`, `sha` (null for a release-only candidate), `judgment` (`confirmed` or `rejected`), `note`, and the current `revision` (0 for the first judgment). Same-origin native writes are required; project grants cannot judge. Invalid notes or window fields return 400, stale or unavailable candidates 409, and an absent issue 404.

Migrations `0070_suspect_decisions.sql` and `0084_suspect_comparisons.sql` are additive. Private archives carry inert judgments, changed-path receipts and coarse cohorts. Project erasure removes all three; owner erasure removes authored judgments and the new metadata stores. Session expiry removes its coarse cohort, and changed paths expire with commit retention. Archives remain subject to the existing erasure and retention restore fences.
