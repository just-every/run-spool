# Personal notifications

In project Settings, each current native person can save their own email choices for resolution, regression, assignment, comment, mention, issue alerts, deploys and weekly reports. All choices start off. Saving sends no mail. Other people’s choices and project rule enablement are independent.

Workflow email goes to current issue subscribers except the actor. Commenting, a resolved mention, an explicit native member or team assignment, a bookmark and Subscribe provide visible subscription reasons. Explicit Unsubscribe takes precedence until Subscribe is used again. Responsibility labels alone remain inert. Deploy email matches the recorded included commit author address to a current project member; this does not verify repository ancestry.

Personal daily and weekly email digests use the timezone and local hour in Settings. Weekly reports share that calendar configuration and remain a separate opt-in. A completed calendar period has one durable delivery identity per person and project. Reports disclose capture loss, held alerts and remaining delivery backlog without embedding event payloads. A started send with an unknown provider result is marked uncertain and is never blindly replayed.

Every personal message includes a Settings link and a narrow one-click link that turns off that notification type in that project. It also cancels queued optional deliveries of that type before their next send. Calendar digest links stop that schedule. An organization administrator can require an enabled rule’s email delivery; members see that requirement in Settings and in mandatory messages. The unsubscribe link still stops optional personal alert email, while an administrator must change mandatory delivery.

Configured rule mailbox destinations that identify a native member obey that person’s current preference and project access. A matching personal alert and a configured rule cannot send the same native person duplicate mail for the same alert. Current authority is checked at claim and immediately before the provider boundary. Removal, a narrowed grant or erasure retires earlier queued authority.

Private archives preserve inert delivery and subscription history. They remove live person bindings, message capabilities and active calendar or mandatory opt-in. Restore never reconnects people or sends mail. Project and owner erasure declare personal delivery, unsubscribe, follow and calendar custody; old archive replay remains fenced.

Slack direct messages and Microsoft Teams personal chats are not connected. Their channel selection and real-provider qualification remain open under TEAM-005, ALERT-002 and ALERT-005. Native hosted email depends on the installation’s approved mail provider and sender configuration; local network-edge qualification is not proof of an external inbox receiving mail.

The native HTTP door is `GET` or `PUT` at `/api/projects/{project}/notifications/preferences`. A save supplies the current `revision` and the complete `email` boolean map with keys `resolution`, `regression`, `assignment`, `comment`, `mention`, `issue_alert`, `deploy` and `weekly_report`. A stale revision is refused. Unknown fields and query selectors are refused; the authenticated person is always the subject, including for an owner or administrator. Project credentials cannot use this door. Removed members and people without current project access cannot read or change preferences.

Read-only collaborators can save their own preferences without changing project policy. Each preference read, save and refusal records a privacy-safe audit fact. Installation-owner erasure removes that person’s preferences and attribution links while keeping permanent safe audit chronology. Downloaded archives remain the holder’s separate custody.

The self-only HTTP doors are `/api/projects/:project/notifications/preferences`, `/api/projects/:project/notifications/digest` and `/api/projects/:project/issues/:issue/bookmark`. Mandatory-rule policy is read under `/api/projects/:project/notifications/mandatory-rules`; only an organization owner or admin can update a selected rule there. Native assignment uses the existing assignment PATCH with an explicit member or project-team target. The original same-origin, current-session and stale-revision fences remain in force.
