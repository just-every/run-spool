# Alert tests, delivery and schedules

Open **Alerts → Rules** to test any configured email or signed-webhook destination. Slack connections and their reviewed tests are managed in **Settings**. Review its passing result, then enable the rule. Test messages say TEST and change no issue, alert, assignment or usage counter. Local development suppresses email and explicitly labels its passing local test. Passing means the observed provider/receiver response; it does not establish mailbox receipt or receiver signature verification. A failing/running result cannot enable a rule. Updating an address disables its rules and retires old queued work; test and review the new address before re-enabling. Enabled rules from an earlier installation keep running until their recipient changes. A disabled rule explains when its destination still needs a passing test and your review.

**Delivery log** keeps transport acceptance separate from recipient state. Email says accepted by provider and, until a signed recipient event arrives, no recipient delivery event yet. The timeline preserves processed, delivered, deferred, bounce, dropped and spamreport; the visible states include delivered, deferred, bounced, dropped and complained. A signed fixture is labelled fixture. A webhook records its observed HTTP status and that the signature header was sent. It never claims that the receiver verified that signature. Slack/Teams message identifiers and PagerDuty/Oncall incident lifecycle inherit ALERT-003 through ALERT-002 before those adapters ship.

## Connect SendGrid delivery events

Create a separate Event Webhook using [SendGrid's multiple-webhooks API](https://www.twilio.com/docs/sendgrid/api-reference/webhooks/create-an-event-webhook), targeting `https://<your-origin>/api/alert-events/sendgrid/<project-id>`. Select processed, delivered, deferred, bounce, dropped and spam_report. Enable signature verification for that webhook ID through [the signed-webhook endpoint](https://www.twilio.com/docs/sendgrid/api-reference/webhooks/toggle-signature-verification-for-an-event-webhook). Keep other account webhooks unchanged. Install its returned public key as `SENDGRID_EVENT_PUBLIC_KEY`, an optional server binding (with `rer deploy --set-secret SENDGRID_EVENT_PUBLIC_KEY --environment <environment>` and the value in a private env file/environment). Use a separate webhook for each project path. Multiple projects may use the same public key if their provider configuration shares it.

Requests have a 256 KiB cap and Base's signature freshness checks. The intake authorizes every event in a batch before writing: `rer_delivery_id` must join a current mail delivery and its exact recipient. Unknown, unsigned or forged requests are refused. Base D1 event IDs are idempotent and conflicting IDs are refused. Raw recipient receipts stay private; the safe per-delivery timeline travels in archives. Provider events do not mark an issue resolved or acknowledged.

`ALERT_EVENT_PROVENANCE=fixture` is only for a test installation using a generated signing key. It labels every projected event fixture. Production defaults to sendgrid. A fixture is never proof of a real provider event.

## Digests and snoozes

Open **Alerts → Digests and snoozes**. The project timezone defaults to UTC; enter a validated IANA name such as America/New_York. Choose daily and/or weekly project mail to a tested/reviewed email destination, and personal daily/weekly mail to the installation owner. Schedules default to 09:00 in that timezone; weekly periods end Monday. Completed calendar periods and unique keys prevent repeated sends across ticks, restarts and DST. The mail includes UTC bounds, totals, the first 50 scrubbed issue summaries, capture receipt usage/loss, failed/overdue Needs attention and held backlog, with no event payload. TEAM-005 inherits member digests; TEAM-001 inherits team digests.

Snooze an issue or rule, or set project maintenance, with a required expiry within one year. Quiet hours use the project timezone and retain notifications in the same held backlog. Capture, event-loss receipts, digest totals and Needs attention continue. Every suppressed delivery remains listed; expiry queues one durable owner resumption notice and never repeats it automatically. Use **Release expired held alerts** when ready to send held work. Active snoozes still fence release. A missing provider blocks a notice visibly; an interrupted send becomes uncertain rather than silently repeating. TEAM-001 inherits team snooze.

## Portability and removal

Additive migration 0058 preserves released data. ERR-009 validators carry `alert_provider_events`, `alert_digest_settings`, `alert_snoozes`, `alert_suppressed` and `alert_scheduled_mail`. Restored schedules and quiet hours are disabled; restored snoozes/scheduled mail are historical and never dispatch. Destination tests and Base's raw mail recipient receipts are excluded from archives. Project and installation-owner erasure explicitly declare these stores, including raw Base receipt/state stores and test results. External provider copies and already delivered mail remain outside installation erasure.

### Slack acknowledgment

A Slack destination uses the same rule windows, durable intents, attempt fences and uncertain-effect reconciliation as a generic webhook. The native adapter is applied only at `INTEGRATION_EGRESS`. A successful Slack `ok: true` response with a valid `ts` records `slack_posted` and displays **posted**, with that timestamp as the message identifier. Recipient receipt stays unconfirmed. API errors, HTTP failures, timeout and missing egress remain visible counted states. The token is never in these records. See [Slack setup and limits](ALERT-WEBHOOKS.md#slack-bot-destination-alert-002). Recorded-edge qualification is not real Slack delivery qualification.
